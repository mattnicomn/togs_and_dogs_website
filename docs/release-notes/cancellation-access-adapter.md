## Concrete inactive adapter boundary

[Adapter](../../src/backend/common/cancellation_access_adapter.py) uses only standard-library dataclasses, Decimal, hashing/JSON, regex, Protocol and URL parsing. It imports none of the existing auth/DB/handler or parent model modules. No source module imports it; there is no SDK client, network, environment/credential read, production token validation, handler registration, persistence or enrollment.

Constructor receives server-owned configured issuers, a Reader and a Verifier. `event_facts` copies only issuer, subject, tenant and group claims from one supported gateway claims shape; it rejects ambiguous REST+HTTP shapes. Headers, credentials, email, body and client role fields are excluded from retained facts. These facts remain untrusted until the configured verifier authenticates and attests them. An event-shaped dictionary is never proof of API Gateway origin.

`GatewayEvidence` binds configured issuer, subject, tenant, customer role, strict integer security epochs and an explicit observation interval. `GatewayAttestation` binds the typed facts/configuration/evidence. Boolean trust flags or digests without a trusted verifier cannot qualify. This slice models only one explicit client group; other/duplicate/ambiguous group sets refuse. No fallback grants a role.

Reader returns an immutable Bundle containing exact REQUEST, complete subject-profile lookup, tenant, lifetime, reservation/receipt observations and LinkProof. Bundle attestation binds query, principal and all typed snapshot content. The adapter requires exact REQUEST keys and persisted tenant/client/request, positive revision and incarnation, initial status, valid ownership field presence/types, no canonical markers, audit LIST-or-absent, no reservation and a live permanent lifetime. It requires exactly one active subject-linked profile with exact tenant/profile keys. LinkProof binds issuer/subject, booking and profile IDs, incarnation/revision, concrete persisted identity fields and provenance ID. A subject or linked-profile identity field must fence the future commit; an email-only fence refuses.

LinkProof is NOT an adopted new stored record schema or provider feature. It represents independently established server evidence. The test verifier maintains a separate authorized-link registry: reading a new, well-shaped link does not automatically authorize it. A valid differing linked client requires an explicitly registered synthetic relationship; absent, forged, stale or conflicting provenance refuses. No client/PET ownership is moved, no profile is created and no mapping is guessed from email/name.

`verify_current` revalidates gateway evidence and the bundle through the trusted verifier, including its actual current-data obligation, before returning evidence. The test verifier compares issued query/principal/snapshot fingerprints against current fixture content and separate provenance authority. Changes to identity, revision, tenant/profile/security state, lifetime/reservation/receipt or provenance invalidate retained evidence even inside the test lease. Typed fingerprints distinguish bool/int equivalence; internal epochs and linkage revisions are exact bounded integers. Integral finite Decimal DB REQUEST revisions normalize at the explicit storage boundary; floats/bools/fractional/nonfinite values refuse. Unknown finite Decimal metadata is preserved.

AccessEvidence always reports activation_ready=False and retains runtime/verifier/freshness/storage/writer/migration/retention/API/release blockers. No commit outcome is produced. Any receipt, including prepared or apparently committed metadata, returns REPLAY_ADAPTER_REQUIRED: a separately designed current historical-replay adapter is still required. Reader/verifier errors abort; they never produce positive access or trigger a retry.

## Synthetic assumptions and real-verifier obligations

[Tests](../../tests/backend/test_cancellation_access_adapter.py) contain the only concrete Reader/Verifier. In-memory issued-fact, current-data and independently authorized-link registries are synthetic provenance, not cryptographic authenticity, actual Cognito behavior, durable storage or demonstrated live concurrency isolation. No real tokens or private records are used. The five-tick lease, exact client-only group shape, active profile and tenant `is_active=True` plus `subscription_status=active` are deliberately restrictive fixture requirements. Compatibility of real tenant/profile forms and production freshness/subscription precedence must be established separately; these checks do not alter runtime policy.

A real server verifier must establish gateway invocation provenance and authorizer configuration, trusted issuer/token audience/use/expiry, nonempty subject and approved role/tenant association; verify issuer-qualified profile linkage and complete duplicate-safe lookup; establish current tenant/revocation evidence; independently authenticate booking linkage provenance; and provide coherent REQUEST/lifetime/reservation/receipt observations with authoritative absence and failure distinction. A shared ID, digest, class, flag or copied email cannot replace these obligations. Do not accept caller-selected dependencies. Cross-system revocation atomicity, identity epochs and current-data consistency are not furnished by existing claims/helper calls or these fixtures.

The compatibility test constructs an exact parent-format Query/Principal/Observation through an explicit test-only bridge. That bridge revalidates current adapter evidence and exact query/observation content before issuing the parent's observation attestation. Parent validation and non-executable preparation pass; a later revision change fails. No production bridge, runtime registration, commit-port call, real transaction, receipt/reservation/lifetime write or ownership enrollment is supplied.

### P1 - Complete commit-time ownership/absence fence

`_bundle` now fails closed (`INCOMPLETE_OWNERSHIP_FENCE`) when any relied-upon persisted identity field (`client_email`, `cognito_sub`, `linked_client_profile_id`) is present on the booking record but absent from the commit fence (`LinkProof.bindings`). Previously only the bound fields were required to match and only a subject/profile identity had to be fenced, so a persisted `client_email` could be left unfenced and therefore not asserted by name in the actual commit transaction. With the completeness guard, every present identity flows through the parent's existing per-binding `#a = :a` condition in PR51's `transaction()` ConditionExpression - an equality that also fails if the attribute is later removed or NULLed. The subject/profile requirement (`IMMUTABLE_OWNERSHIP_FENCE_REQUIRED`, email-only still refuses) is preserved. The guard needs no PR51/PR52 change; the extra binding is carried by the unchanged per-binding condition. Where an absence guard cannot be expressed without changing PR51, the adapter fails closed rather than widening the parent contract.

### P2 - Exact tenant metadata identity

`ACTIVE_TENANT_REQUIRED` now additionally requires `tenant.get("company_id") == query.tenant`, so the persisted tenant-metadata record's own `company_id` must exactly equal the trusted selected tenant. Missing, NULL, malformed or contradictory `company_id` values are rejected. The conservative active-status policy (`is_active is True`, `subscription_status == "active"`, exact `PK`/`SK`) is unchanged. The positive synthetic tenant fixture was aligned to include the documented `company_id`.

### Targeted regressions added (six)

`test_persisted_identity_field_absent_from_commit_fence_fails_closed`, `test_every_present_identity_field_is_in_the_returned_commit_fence`, `test_actual_pr51_condition_expression_pins_every_fenced_identity_and_revision` (drives the real PR51 `transaction()` and asserts each fenced identity plus revision/incarnation appears as a named condition), `test_actual_commit_refuses_changed_removed_null_or_inserted_identity` (drives the real parent `validate_observation` with synthetic post-preparation identity mutations - changed/removed/NULL/inserted - each refuses), `test_tenant_metadata_company_id_must_exactly_match_selected_tenant`, and `test_tenant_metadata_exact_company_id_positive_fixture_is_aligned`. Positive fixtures were aligned: tenant metadata carries `company_id`; the default `LinkProof.bindings` fences all three present identities; two subject-less cases drop `client_email` so the fence stays complete.
