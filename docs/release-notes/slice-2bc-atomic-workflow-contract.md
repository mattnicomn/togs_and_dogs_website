## Pure contract and atomic request shape

[Contract](../../src/backend/common/atomic_workflow_contract.py) imports only dataclasses/hashlib/json/re. No SDK, client, filesystem/network operation, transaction execution or production import. [Tests and simulated store](../../tests/backend/test_atomic_workflow_contract.py) interpret complete DynamoDB expressions in memory and publish state only after every condition passes. No client/table/mock AWS service is invoked; this is not a proof of real database isolation.

Frozen tenant/key/record/operation/effect identities use canonical immutable JSON bodies. Bodies bind exact company/client/request/PET IDs. Both before and after aggregates must enumerate precisely the parent's unique LIST job_ids/pet_ids and all linked children/PETs, with no extra/missing/wrong-tenant records. JOB pet references must belong to that parent; PET ownership must match the client. New children/PETs and parent references commit together. No inferred primary job, orphan fallback, legacy scalar membership or client remapping is introduced.

Each existing record has a strict positive bounded integer `legacy_write_revision` and immutable `record_incarnation`; updates increment by one. Complete observed fields, revision/incarnation, and absence of every enumerated canonical/provisioning marker are conditional at commit time, including NULL/partial/unsupported markers. Unchanged siblings/PETs are conditional checks, serializing parent and sibling races conservatively. New records use create-only conditions. Hard deletes are refused; no destructive recovery/compensation is supplied. Cancellation preserves completed children; parent completion cannot precede all child completion. Reassignment with Start evidence remains policy-pending/refused, not an adopted new runtime rule. These are storage consistency assumptions, never RBAC or lifecycle approval.

**Permanent identity/non-reuse:** exact tenant+PK+SK maps to a domain-separated SHA-256 key. `RESERVATION#<digest>/PERMANENT` must be absent in the same transaction. A separate prospective `LIFETIME#<digest>/PERMANENT` witness binds the exact immutable incarnation and non-retired state; creation is create-only, old lifetimes are never reused. Witness checks reject expiration fields `ttl`/`expires_at`; no expiration/removal path exists here. Existing identities without a witness are refused, not automatically backfilled. This is construction/validation and offline shape only: no actual reservation or witness is created, and the approved non-expiring reservation policy is unchanged. Retirement/deletion/backup restoration protocol and namespace adoption require separate review before any adapter.

**Important limits demonstrated by characterization tests:** an unfenced writer can delete/recreate byte-identical data without retiring the witness, and an unversioned writer can add an unknown field that a later whole-record replacement loses. This model cannot detect those bypasses; both tests deliberately demonstrate them. All-writer fencing, field-preserving adapters or a revised envelope, durable witness protection and mixed-version controls are absolute activation blockers. No claim of globally solved ABA or safe production replacement is made. Restoring the entire journal/data to an earlier identical state is not detectable by these predicates.

Operation receipt and all outbox intents are in the same proposed transaction as affected records and lifetime checks. Receipt binds the full operation, before/after data and effects, and retains an immutable plan document for recovery. Repeat same binding returns persisted evidence; same operation with changed input refuses. This relies on durable receipt retention and authoritative re-read after commit timeout; no receipt regeneration or provider token window substitutes for it. Receipts/effect plans must never carry secrets or credentials; production minimization/redaction and retention are pending.

Request builders target distinct items with conditions folded into the Put/Update for an item being changed. Conservative local limits: at most 100 actions; estimated encoded budget below 3 MiB total and 350 KiB per action; expression <=4096 bytes; JSON nesting <=16. Oversize refuses before persistence/effects; no chunked partial booking or automatic splitting is authorized. These are deliberately stricter design budgets, not an exact DynamoDB size calculator. AWS independently enforces item/transaction limits. [Official TransactWriteItems reference](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_TransactWriteItems.html): 100 actions, distinct items, 4 MB aggregate, 400 KB item; provider request-token idempotency has a 10-minute window, so durable receipts are still required.

## Post-commit effect lifecycle and recovery

| Durable state / result | Permitted modeled action / truthful meaning |
| --- | --- |
| Conditional commit refused/conflict/oversize | No modeled records/intents/effects published; report refusal, never full/partial success. Do not unconditional-retry. |
| PERSISTED_EFFECTS_PENDING | Records/receipt/intents committed; does NOT claim Calendar/notification delivery. |
| PENDING | CAS claim checks operation binding, intent revision/state, current full aggregate, lifetime and reservation conditions; receipt must match. |
| CLAIMED | One claim ID binds the attempted effect. Interrupt before or after invocation remains ambiguous; another coordinator cannot blindly resend. |
| DONE | Matching claim reports applied, or trusted authoritative bound evidence confirms applied. No further attempt. |
| HOLD | Timeout or reported failure retains ambiguity; no automatic retry. |
| Authoritative NOT_APPLIED | Current verified evidence bound to tenant/operation/effect/payload binding/claim may return to PENDING, with new revision. Evidence must cover the old attempt definitively, not an eventually consistent absence or a still-running timed-out call. |
| Superseding cancellation/other mutation | Stale aggregate cannot claim/requeue/ack through this builder. Manual reconciliation is required; already-issued effects cannot be undone by a database rollback. |

Pure transition functions require expected versions; claim/report/reconciliation request shapes additionally fence the stored receipt/outbox and aggregate. The synthetic backing store performs these checks together. Trusted evidence flags are adapter preconditions, not signature verification or public inputs. No real Calendar/notification provenance, exactly-once delivery, authoritative absence, fencing-token support or safe provider retry guarantee is asserted. If a provider cannot prove non-application and quiescence, remain held for owner-directed reconciliation. A late cancellation cannot revoke an already-issued provider call. Independent notification/Calendar failures leave committed records intact and other effect states separate; rollback is a new conditional operation, not deletion of receipts or reversal of delivered messages.
